## Summary

When an AI stops partway through a task, it writes a checkpoint that records:

1. the task, its success criteria, and what is done and next;
2. each statement that matters, with its source and whether anyone checked it;
3. the files and records involved, by reference;
4. the approvals and actions still pending, and whether repeating one is safe.

Another model, agent, or app reads the checkpoint and continues the work. The checkpoint grants
it no permissions.

## What is a checkpoint?

A JSON document that holds the state of one unfinished task: where the work stands, what is
pending, and where each fact came from. It leaves out the conversation that produced the work, so
it stays a few kilobytes.

## Why not pass along a summary?

A prose summary carries the facts and drops their sources. Your instruction, the AI's guess, and a
line pasted from a customer email all read as plain sentences. A checkpoint labels each one, so the
next AI follows your instruction, re-checks the guess, and treats the email as a quote.

The fields also let software check the work. A validator rejects a malformed checkpoint before any
model reads it. A runtime can hold a pending approval or enforce a stop condition without relying
on the model to remember it.

## Who writes one, and who reads it?

An AI agent, or the application around it, writes one when a session ends, its context fills, or
the work moves to another tool. The reader can be another model, another vendor's agent, or the
same agent next week.

## How do I write a good checkpoint?

<ul class="oc-rules">
  <li>
    <strong>Record where the work stands.</strong> Leave out the turns that got it there.
  </li>
  <li>
    <strong>Label every statement.</strong> Give each one a kind and an origin.
  </li>
  <li>
    <strong>Quote outside content.</strong> Record text from an email, a web page, or a tool result
    as <code>external</code>. It never becomes an instruction.
  </li>
  <li>
    <strong>Say what you checked.</strong> Mark verified facts, and say when the reader should check
    them again.
  </li>
  <li>
    <strong>List what is pending.</strong> Put an approval you're waiting on, or a payment you
    started, in <code>operations</code>.
  </li>
  <li>
    <strong>Point to resources.</strong> Reference files and records by system and key instead of
    copying them in.
  </li>
  <li>
    <strong>Grant nothing.</strong> The reader acts with its own tools and its own authority.
  </li>
</ul>

### Kinds of statement

<dl class="oc-kinds">
  <dt>
    <code>instruction</code>
  </dt>
  <dd>Something a person asked for.</dd>
  <dt>
    <code>constraint</code>
  </dt>
  <dd>A limit the work must respect.</dd>
  <dt>
    <code>decision</code>
  </dt>
  <dd>A choice already made, with its reason.</dd>
  <dt>
    <code>observation</code>
  </dt>
  <dd>Something seen in a tool, file, or system.</dd>
  <dt>
    <code>hypothesis</code>
  </dt>
  <dd>A guess that needs checking.</dd>
  <dt>
    <code>question</code>
  </dt>
  <dd>Something nobody has answered yet.</dd>
  <dt>
    <code>external</code>
  </dt>
  <dd>Content quoted from outside the session.</dd>
</dl>

## Can a checkpoint be wrong?

Yes. A model writes it, and anyone can edit it afterward. So the reader re-checks verified facts
before acting on them, reads approvals from the system that grants them, and treats the checkpoint
as a starting point. A validator rejects a checkpoint that breaks the format's rules, and you get
an error instead of a quiet mistake. [Security considerations](security/) covers the details.

## Frequently asked questions

### Is a checkpoint the same as memory?

No. Memory keeps facts across many tasks. A checkpoint holds one task's state until someone
resumes it. [Checkpoints and memory](concepts/#checkpoints-and-memory) explains the difference.

### Does it compete with MCP or A2A?

No. Those protocols connect agents to tools and to each other. A checkpoint is a document, and
either protocol, or a plain file, can carry it. See [MCP](interop/mcp/) and [A2A](interop/a2a/).

### Can I hand one checkpoint to several agents?

Yes. The specification covers [forking](forking/), including which copy owns each pending action,
so two agents never act on the same one.

### Is it stable?

Not yet. Version 0.1 is a draft open for review, and fields may change before 1.0.

### How can I contribute?

Read the draft, try it with your agent, and open an issue or a pull request.
